01

What is version control?

0:00 – 0:03

Before Git makes sense, you need to understand the problem it solves.

Imagine you're writing an essay. You save it as essay.docx. The next day you make big changes and want to keep the old version too, so you save a copy: essay_final.docx. Then you edit again: essay_final_v2.docx, essay_final_REALLY.docx...

This is what people did before version control — and it breaks down fast. You lose track of what changed, why, and which file is actually current.

Definition

Version control is a system that automatically records every change to your files over time — what changed, when, and why — so you can view, compare, or restore any previous version without manually renaming files.

Git is the most widely used version control system in the world. It was created in 2005 by Linus Torvalds (also the creator of Linux) to manage the Linux kernel's source code.

02

Git vs GitHub

0:03 – 0:07

The single most confusing thing for beginners — and it's simpler than it sounds.

Git is a tool installed on your computer. It tracks changes to files in a folder. It works completely offline and needs no internet connection.

GitHub is a website that hosts Git repositories online. It adds a place to store your code in the cloud, share it with others, and collaborate through features like Pull Requests and Issues.

GitGitHub
What it isSoftware on your machineA cloud platform
Works offlineYesNo — needs internet
JobTracks changes, historyStores & shares repos online
AlternativesMercurial, SVNGitLab, Bitbucket
Mental model

Git is the engine in your car. GitHub is the public parking garage where you can leave your car for others to see, borrow, or work on with you.

03

Install & first-time setup

0:07 – 0:12

Do this once per computer, and you're set for life.

1. Install Git

  • Windows: download and run the installer from git-scm.com — this gives you Git Bash, the terminal you've been using.
  • Mac: open Terminal and type git --version — it will prompt you to install if missing.
  • Linux: sudo apt install git (Debian/Ubuntu) or your distro's equivalent.

2. Tell Git who you are

Every commit is stamped with a name and email. Set these once:

bash
$ git config --global user.name "Your Name" $ git config --global user.email "you@example.com" $ git config --list # verify it saved

3. Create a GitHub account

Sign up free at github.com. This is where your repos will live online.

04

Turning a folder into a repo

0:12 – 0:16

How Git actually starts tracking a project.

Open a terminal inside any project folder and check what's there:

~/Test
$ ls -a ./ ../ # just a plain, untracked folder

Now initialize it as a Git repository:

~/Test
$ git init Initialized empty Git repository in ~/Test/.git/ $ ls -a ./ ../ .git/ # the hidden .git/ folder is where ALL history lives
Good to know

The .git folder is the entire database of your project's history. Delete it, and you lose all Git tracking — the files themselves stay, but the history is gone forever.

05

The three areas of Git

0:16 – 0:20

This one idea unlocks everything else. Every file lives in one of three places.

Working directory
Files you're editing right now
→git add
Staging area
Changes marked "ready to save"
→git commit
Repository
Permanently saved snapshot

Think of the staging area like a shopping cart. You add items to it (git add), review what's inside (git status), and only when you're happy do you "check out" — which in Git terms is committing (git commit).

Why staging exists

It lets you commit only some of your changes at a time. Changed five files but only two are related? Stage and commit just those two, with a message that actually describes them.

06

Core commands in action

0:20 – 0:32

A full walkthrough, start to finish, on a real example.

git status — what's going on?

Your most-used command. Run it constantly — it never breaks anything, it just reports.

~/Test (master)
$ git status On branch master No commits yet Untracked files: index.html

git add — stage your changes

~/Test (master)
$ git add index.html # stage ONE file $ git add . # stage ALL changed files $ git add --all # same as above, explicit form
Common typo

git add. and git .add both fail — Git reads them as unknown commands. The space matters: it's git add . — three separate words.

git commit — save the snapshot

~/Test (master)
$ git commit -m "Add homepage markup" [master (root-commit) a1f9c3e] Add homepage markup 1 file changed, 12 insertions(+)
Common mistake

The message MUST be in quotes: git commit -m "message". Without quotes, Git treats each word as a separate file name and throws pathspec did not match any files.

Writing good commit messages

✓ Good

"Add login form validation"
"Fix cart total rounding bug"

✗ Avoid

"changes"
"fixed stuff again"
07

Reading history: log & diff

0:32 – 0:36

Once you've made a few commits, here's how to look back at them.

git log — the full history

~/Test (master)
$ git log commit a1f9c3e... Author: Your Name <you@example.com> Date: Tue Aug 18 2026 Add homepage markup

Tip: git log --oneline compresses each commit into a single line — much easier to scan.

git diff — what actually changed

~/Test (master)
$ git diff - console.log("Hello") + console.log("Hello World")

Rule of thumb: git diff = "what did I just change?" · git log = "what have I done over time?"

08

Branching & merging

0:36 – 0:42

Work on new ideas without touching the code that already works.

A branch is an independent line of development. The default branch is usually called main or master. When you want to build a new feature, you spin off a new branch, work there safely, then merge it back once it's done.

main
feature/nav

The feature branch splits off, gets its own commits, then merges back into main.

bash
$ git branch # list branches $ git checkout -b feature/navbar # create + switch, in one step $ git add . && git commit -m "Add navbar" $ git checkout main # switch back $ git merge feature/navbar # bring the work into main
09

Merge conflicts

0:42 – 0:46

What happens when two branches change the same line — and how to fix it calmly.

A conflict happens when Git can't automatically decide which version of a line to keep. It pauses the merge and marks the file for you to resolve by hand.

app.js
<<<<<<< HEAD console.log("Version A") ======= console.log("Version B") >>>>>>> feature/logging
  1. Open the file — Git marks conflicting sections with <<<<<<<, =======, >>>>>>>.
  2. Decide which version to keep (or combine both).
  3. Delete the marker lines entirely.
  4. Save, then git add . and git commit to finish the merge.
Don't panic

Conflicts are a normal, expected part of collaborating — not a sign something is broken. Take your time reading both versions before choosing.

10

Connecting to GitHub

0:46 – 0:52

Getting your local repo online — and keeping it in sync.

1. Create a repository on GitHub

On github.com, click New repository, name it, and don't initialize it with a README (you already have local commits).

2. Link your local folder to it

bash
$ git remote add origin https://github.com/you/repo.git $ git branch -M main $ git push -u origin main Enumerating objects... done. → pushed to GitHub

origin is just a nickname Git gives your remote URL — you'll type "origin" instead of the full link from now on.

3. Daily sync

bash
$ git push # send your new commits up $ git pull # bring teammates' commits down $ git clone <url> # download someone else's repo, first time
Habit to build

Always git pull before you start working, and before you git push. It keeps you in sync with any changes made elsewhere and avoids most conflicts.

11

Undoing mistakes

0:52 – 0:55

Everyone makes mistakes in Git. Here's how to recover from the common ones.

Unstage a file

git reset HEAD fileKeeps changes, removes from staging

Discard local edits

git restore fileReverts file to last commit — unrecoverable

Fix last commit message

git commit --amend -m "..."Only before pushing

Undo a commit safely

git revert <hash>Adds a new commit that reverses it
Handle with care

git reset --hard <hash> rewinds your branch and permanently discards commits after that point. Prefer git revert — it undoes changes without erasing history.

12

Best practices

0:55 – 0:58

Habits that separate a smooth workflow from a painful one.

  • Commit small, related changes often — not one giant commit at the end of the day.
  • Write commit messages that explain what and why, in present tense.
  • Never commit passwords, API keys, or credentials — use a .gitignore file to exclude them.
  • Pull before you push, every time, to avoid unnecessary conflicts.
  • Do risky or experimental work on a branch, never directly on main.
  • Keep main always in a working, deployable state.
